# Troubleshooting

Use these checks to diagnose common Temporal Python integration errors.

## Worker Does Not Connect to OpenBox

Check the Worker environment:

```bash
[ -n "$OPENBOX_URL" ] && echo "OPENBOX_URL is set" || echo "OPENBOX_URL is NOT set"
[ -n "$OPENBOX_API_KEY" ] && echo "OPENBOX_API_KEY is set" || echo "OPENBOX_API_KEY is NOT set"
```

Then complete these checks:

1. Confirm that `OPENBOX_URL` and `OPENBOX_API_KEY` are set in the Worker process.
2. Start the Worker.
3. Check the logs for OpenBox initialization errors.
4. Start a Workflow.
5. Confirm that a session appears in the OpenBox console.

## Sessions Do Not Appear

Complete these checks:

1. Confirm that the Worker is running and connected to OpenBox.
2. Find `OpenBox SDK initialized successfully` in the Worker logs.
3. Confirm that the Workflow completed in the [Temporal UI](http://localhost:8233).
4. Confirm that the API key belongs to the registered OpenBox agent.

## Governed Command Support Is Not Configured

A registered command can report `GovernedCommandConfigurationRequired` when its Worker lacks sandbox configuration.

Complete these checks:

1. Confirm that the Worker uses `plugins=[OpenBoxPlugin(...)]`.
2. Confirm that the same plugin receives `sandbox=SandboxConfig(registry=command_registry)`.
3. Confirm that the requested profile exists in the registry.
4. Run `obs status`.
5. Confirm that the status reports the intended provider.
6. Load `~/.config/openbox-sandbox/agent.env` into the Worker process.
7. Confirm that the service, policy, and mTLS paths from that file exist.

Keep Worker registration and interception in the same `OpenBoxPlugin` initializer. The launcher does not select another provider when provisioning fails.

See [Command Profiles](/developer-guide/temporal-python/command-profiles) for the supported configuration.

## Sandbox Provisioning Fails

Provisioning fails closed when it cannot verify a provider, policy, or release asset.

Complete these checks:

1. Confirm that the launcher, service, policy templates, `SHA256SUMS`, and SBOM files came from one release.
2. Verify `SHA256SUMS` before provisioning. Use `shasum -a 256 -c SHA256SUMS` on macOS. Use `sha256sum -c SHA256SUMS` on Linux.
3. Confirm the selected provider with `--provider native|openshell` or `OPENBOX_PROVIDER`.
4. Run `obs status` to inspect current state.
5. Run provisioning again with `--clean-rerun --yes`.
6. Run `obs verify` to test the live mTLS lifecycle.

`--yes` does not bypass verification or platform requirements. `--clean-rerun` removes launcher-owned runtime state. It does not permit provider fallback.

See [Provisioning](/developer-guide/temporal-python/provisioning) for provider and policy details.

## Sandbox Demo Cannot Reach example.com

The demo requires `policy-allow-network-dev.yaml`. That policy permits `/usr/bin/curl` to reach only `example.com:443`.

Provision the required policy:

```bash
obs provision --provider native --clean-rerun --yes \
  --policy-file "$PWD/policy-allow-network-dev.yaml"
```

Then complete these checks:

1. Load the generated `agent.env` file into the Worker process.
2. Restart the Worker.
3. Confirm that the registered profile is `example-egress`.
4. Run `obs verify`.
5. Inspect `openbox.sandbox.egress.<n>.decision`, `.host`, and `.port` in the `sandbox_execution` span.

The demo must fail closed when the selected policy does not permit the destination.

## Governance Blocks or Stops the Agent

A blocking rule causes a non-retryable `GovernanceBlock` or `GovernanceHalt` error. This result confirms that the plugin enforced the governance decision.

To inspect the decision:

1. Open the [OpenBox console](https://platform.openbox.ai).
2. Open the agent **Overview** tab.
3. Open the session.
4. Identify the rule that caused the block or halt.

See [Error Handling](/developer-guide/temporal-python/error-handling) for governance and approval error handling.

## Approval Requests Do Not Appear

Complete these checks:

1. Confirm that the behavioral rule uses **Require Approval**, not **Block**.
2. Confirm that the agent trust tier matches the rule conditions.
3. Confirm that the approval timeout has not expired.

See [Approvals](/approvals) for approval queue behavior.

## LLM API Calls Fail

The demo uses [LiteLLM](https://docs.litellm.ai/docs/providers) for model routing. `LLM_MODEL` uses the `provider/model-name` format.

Common values are:

| Provider | Example `LLM_MODEL` value |
|---|---|
| OpenAI | `openai/gpt-4o` |
| Anthropic | `anthropic/claude-sonnet-4-5-20250929` |
| Google AI | `gemini/gemini-2.0-flash` |

Confirm that `LLM_MODEL` and `LLM_KEY` are correct in `.env`.

Run this test from the project directory:

<Tabs>
<TabItem value="uv" label="uv" default>

```bash
uv run python3 -c "
import os
from dotenv import load_dotenv
load_dotenv()
from litellm import completion
response = completion(
    model=os.getenv('LLM_MODEL'),
    api_key=os.getenv('LLM_KEY'),
    messages=[{'role': 'user', 'content': 'test'}]
)
print(response.choices[0].message.content)
"
```

</TabItem>

## Temporal Server Does Not Run

The Worker reports this error when it cannot connect to the local Temporal server:

```text
Connection refused: localhost:7233
```

Start the development server:

```bash
temporal server start-dev
```

Open the Temporal UI at [http://localhost:8233](http://localhost:8233).
